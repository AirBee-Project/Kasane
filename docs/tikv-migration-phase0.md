# TiKV 移行 Phase 0：技術検証の結果

LMDB(heed) から TiKV へバックエンドを移行するにあたり、設計の前提として置いていた性質を
実測で確認した記録。**測定の結果、当初の設計を 2 点修正している**（末尾の「設計への影響」参照）。

検証環境：`deployment/tikv/docker-compose.yml`（TiKV v7.5.1 単一ノード）、`tikv-client` 0.3.0。

## 検証結果

| # | 検証項目 | 結果 |
|---|---|---|
| 1 | `heed::RoTxn<WithoutTls>` / `RwTxn` / `Env` の `Send` 性 | いずれも `Send`。スレッドを跨いだ実行も Windows 上では成功 |
| 2 | `tikv-client` のビルド | 0.3.0 は protoc 不要でビルドできる |
| 3 | read-your-writes | トランザクション内で自分の未コミット書き込み・削除が読める |
| 4 | 存在しないキーへの悲観ロック | 取得できる（ガードキー方式が成立する） |
| 5 | 悲観ロックの排他性 | 他トランザクションは待たされる（実測 2.0 秒保持 → 待機側が 2.03 秒でブロック解除） |
| 6 | プレフィックススキャンの順序 | バイト辞書順。LMDB と同じ順序保証 |
| 7 | ガードキーによる直列化 | **素朴な方式では lost update が発生**（下記参照） |

## 発見 1：悲観ロックの `PessimisticRetry` はクライアントがリトライしない

ロック保持者がコミットすると、待機していた側は
`WriteConflict { reason: PessimisticRetry }` を受け取る。`tikv-client` 0.3.0 の
`pessimistic_lock` は `for_update_ts` を取り直すものの、このエラーを内部でリトライせず
呼び出し側へ返す（`transaction.rs:844-856`）。

したがって**アプリケーション側にリトライループが必須**。LMDB では「書き込みは待たされることは
あっても失敗しない」が、TiKV ではリトライを自前で実装して初めてその性質が再現される。

## 発見 2：ガードキーを作業トランザクション内で取ると lost update が起きる

「1 つのトランザクション内でガードキーをロックしてから読み書きする」方式は**安全ではない**。

- 悲観ロックは取得時に PD から取り直した `for_update_ts` で取られる
- 一方 `txn.get()` はトランザクション開始時の `start_ts` スナップショットを読む
- よって「`start_ts` 〜 ロック取得」の間に他者がコミットした変更が**見えない**
- ロックは正しく排他されているのに古い値を読んで上書きし、lost update になる

実測：16 並行の read-modify-write でカウンタが **15**（1 件消失）。

### 採用する方式：ロック用トランザクションと作業トランザクションを分ける

LMDB の `env.write_txn()` は「ライタミューテックス取得 → スナップショット確定」の順に行う。
この順序を 2 つのトランザクションに分けて忠実に再現する。

1. ロック専用トランザクションでガードキーを取得（ミューテックス取得に相当）
2. **その後に**作業用トランザクションを開始する
   → `start_ts` が確実に前任者のコミットより後になる（PD のタイムスタンプは単調増加）
3. 作業をコミット
4. ロック専用トランザクションを `rollback()` して解放

ロック専用トランザクションは常に `rollback` で終わるため、ガードキーには MVCC の
バージョンが一切作られない。よって待機側が `PessimisticRetry` を踏む機会も減る。

実測：同じ 16 並行テストでカウンタが **16**（消失なし）。

## 発見 3：単一グローバルロックでは高競合時のリトライ率が高い

上記の方式で 16 タスクが**同一のガードキー**を奪い合った場合、16 回の成功に対して
延べ 114 回の試行が必要だった（約 7 倍）。

これは「グローバル 1 本のロック」を避け、既に計画している**階層ロック**
（データベース単位 / テーブル単位）で競合範囲を絞る方針の妥当性を裏付ける。
無関係なテーブルへの書き込み同士はそもそもロックを奪い合わない。

## 発見 4：LMDB の書き込みトランザクションはスレッドに固定すべき

`RwTxn` は `Send` であり、実測でもスレッドを跨いで使用できた（Windows）。しかし LMDB の
公式ドキュメントは「書き込みトランザクションは単一スレッドからのみ使用すること」を要求しており、
POSIX ではライタミューテックスの所有スレッド制約がある。デプロイ先は Linux であるため、
**この挙動に依存しない**設計にする。

具体的には、LMDB バックエンドの書き込みトランザクションは 1 つの blocking タスクに固定し、
そのタスク内で `Env` の保持・トランザクション開始・全操作・コミットまでを完結させる。
これは 'static ライフタイム問題（`RwTxn<'a>` を `spawn_blocking` へ渡せない）も同時に解消し、
unsafe な自己参照構造を避けられる。ブロッキングスレッドの占有コストは、現行実装が
サービス層で `spawn_blocking` を 1 操作ごとに使っているのと同等で、後退しない。

## 設計への影響

### 1. リポジトリ層の API はクロージャ方式にする（ハンドル方式から変更）

書き込みが競合でやり直しになりうる以上、**書き込み操作全体が再実行可能**でなければならない。
`begin_write()` でハンドルを返し呼び出し側が手続き的に操作する方式では、
リポジトリ層がリトライを透過的に行えない。

```rust
// 採用：クロージャ方式（リトライはリポジトリ層の内部に閉じる）
storage.write(|w| async move { w.database_create(&name, desc).await }).await?;
```

リトライループを `Storage` 実装の内部に閉じることで、サービス層は競合の存在を知らずに済み、
「書き込みは待たされても失敗しない」という LMDB の性質がそのまま保たれる。

### 2. 階層ロックの取得は作業トランザクションの外側で行う

前掲の 2 トランザクション方式により、階層ロック（DB 単位 / テーブル単位）の取得は
すべて外側のロック用トランザクションで行い、その後に作業トランザクションを開始する。
複数階層のロックが必要な操作は、外側のロック用トランザクションで
「DB 単位 → テーブル単位」の順に取得する（デッドロック回避のための順序規約は不変）。

## 階層ロックの実測（Phase 3）

「外側ロックトランザクション + 内側作業トランザクション」に、データベース単位 /
テーブル単位の階層ロックを組み合わせた構成を、同じクラスタで測定した。

| 検証 | 結果 |
|---|---|
| 同一スコープへの 16 並行書き込み | カウンタ = 16（lost update なし）。延べ 120 試行、472 ms |
| **別スコープ**への 16 並行書き込み | 延べ **16 試行（リトライ 0）**、**47.8 ms** |
| DB→テーブルの順序を守る 12 並行書き込み（単一ロックと二重ロックの混在） | デッドロックなし |

無関係なスコープ同士は競合せず、同一スコープの場合と比べて**約 10 倍速い**。
グローバル 1 本のロックを避けて階層化する設計判断が、実測で裏付けられた形になる。

3 番目の検証は「`data_insert` 相当（テーブルロックのみ）」と「`table_remove` 相当
（DB ロック → テーブルロック）」を混在させたもの。全操作が同じ順序でロックを取る限り
待ちグラフに循環ができないことを、実際の並行実行で確認している。

## 再現方法

docker compose -f deployment/tikv/docker-compose.yml up -d
