# Kasane トレーシング・ポリシー

このドキュメントでは、Kasaneプロジェクトにおけるトレーシング（ログ出力）のポリシーを定めます。過剰なトレーシングによるログの肥大化やパフォーマンスの低下を防ぎつつ、システムの状態を正しく把握できる高い可観測性（Observability）を維持することを目的としています。

## 基本方針

私たちは「関数ごとの細かい実行時間の計測」よりも、「リクエスト全体のレイテンシとステータスの把握」を優先します。不要にネストされたスパン（Span）はログをノイズだらけにし、実際のエラーや重要なビジネスイベントを見つけにくくします。

### 1. HTTP/アプリケーション境界 (Edge)
- **ポリシー:** リクエストとレスポンスの記録は `tower_http::trace` に一任します。
- **詳細:** `TraceLayer` により、HTTPメソッド、URI、全体的なレイテンシ、レスポンスのステータスコードが自動的に記録されます。APIのパフォーマンスや使用状況の追跡には、これで十分な可視性が得られます。

### 2. ハンドラー層 (Handlers / Presentation Layer)
- **ポリシー:** 原則として `#[tracing::instrument]` は**使用しません**。
- **詳細:** ハンドラーは主に、HTTPリクエストからデータを受け取り、サービス層へとルーティングするだけのパススルー（中継）関数です。ここに `instrument` を付与しても、`tower_http` のスパンとほぼ同じ内容が重複して記録されるだけであり、冗長になります。

### 3. サービス層 (Services / Business Logic Layer)
- **ポリシー:** 単純なCRUDやパススルー処理に `#[tracing::instrument]` は**使用しません**。複雑なオーケストレーションを伴う処理にのみ使用を検討します。
- **詳細:** サービスメソッドが単にリポジトリメソッドを呼び出すだけの場合はトレースを付与しないでください。「バリデーションの失敗」や「キャッシュの再構築」といったビジネス上重要な意味を持つイベントに対してのみ、手動で `tracing::info!`、`tracing::warn!`、または `tracing::error!` を使用してください。

### 4. リポジトリ層 (Repositories / Data Access Table)
- **ポリシー:** 原則として `#[tracing::instrument]` は**使用しません**。
- **詳細:** データベース操作は高頻度で発生します。すべてのDBの読み書き操作に対してスパンを作成すると、深刻なログの肥大化とパフォーマンス低下を招きます。エラーは `Result::Err` として返し、必要に応じて上位のレイヤーでログ出力されるようにハンドリングします。特定のクエリのプロファイリング（性能測定）が必要な場合に限り、一時的に `debug!` や `trace!` を使用します。

## 各ログレベルの使い分け

- **`error!`**: クリティカルな障害、予期せぬデータベースの切断、システムにおける不変条件の破壊（あってはならない状態）などに使用します。（注: 通常の `AppError` はHTTPステータスコードに変換され、`tower_http` が自動的に4xx/5xxとして記録します）
- **`warn!`**: 致命的ではないエラー、代替処理（フォールバック）の発生、不審だが仕様上有効なリクエストなどに使用します。
- **`info!`**: 「データベースの初期化完了」や「サーバーの起動」など、ライフサイクル上の主要なイベントに使用します。**すべての関数の開始を告げる目的で `info!` を使用しないでください**（例: APIパスから明らかであるにも関わらず `info!("Creating table...")` のようにログを出さないこと）。
- **`debug!` / `trace!`**: ローカル開発時に、内部状態を詳細に出力したい場合に使用します。これらは本番環境ではデフォルトで無効化されます。
